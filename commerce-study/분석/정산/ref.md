톡켓의 정산 시스템을 만든다면, 저는 Blnk, Formance Ledger, Medusa/Mercur, Stripe Connect, Adyen for Platforms 이 다섯 가지를 가장 먼저 분석하겠습니다.

특히 톡켓은 일반적인 쇼핑몰 정산보다 복잡한 구조로 발전할 가능성이 높습니다.

예를 들어 대학 축제 하나에서 티켓 판매대금이 발생했을 때 학생회, 공연기획사, 협찬 유치사, 현장 운영사, 톡켓이 각각 수익을 배분받을 수 있습니다. 여기에 결제 수수료, 부분 환불, 행사 취소, 정산 보류, 지급 일정까지 관리해야 합니다.

따라서 처음부터 다음 세 가지를 분리해서 설계하는 것이 중요합니다.
- Revenue Sharing: 거래 금액을 어떤 파트너에게 얼마씩 배분할 것인가?
- Ledger: 각 파트너에게 얼마를 지급해야 하는지 정확하게 기록하고 추적할 것인가?
- Settlement & Payout: 언제 정산을 확정하고, 실제 계좌에 얼마를 송금할 것인가?
이 세 영역을 분리하면 향후 협찬, 광고, 여행, 공동구매 등의 상품으로 확장하더라도 기존 정산 시스템을 재사용하기 쉬워집니다.

설계 요소	고려사항
정산 계약	행사별 고정금, 정률, 단계별 수수료, 최소 보장금

파트너 지급	지급 보류, 지급 실패, 재시도, 마이너스 잔액
대사	PG 정산자료, 은행 거래, 내부 원장 차이 검증

톡켓에서는 특히 세 가지를 추가로 강조하겠습니다.

첫째, 정산 규칙의 버전 관리가 필요합니다. 계약 조건이 바뀌더라도 이전 주문에는 당시 확정된 계약 버전이 유지돼야 합니다.

둘째, Ledger와 정산 명세서는 다른 개념입니다. 원장은 거래의 재무적 사실을 기록하고, 명세서는 특정 기간의 거래를 파트너별로 집계해서 확정하는 스냅샷입니다.

셋째, 정산은 반드시 대사 기능을 포함해야 합니다. 내부 계산 결과와 PG에서 실제 지급한 금액이 다르면 자동으로 차이를 발견하고 사람이 검토할 수 있어야 합니다. Blnk에도 외부 거래 내역과의 대사 기능이 제공됩니다.

5. 개발 순서 추천
톡켓은 이미 NestJS Modular Monolith, TypeORM, Aurora MySQL을 사용하므로 처음부터 별도 금융 서비스를 다수 도입하지 않아도 됩니다.

1단계 — 원장 및 정산 도메인 정의

Modern Treasury, Blnk, Mercur의 데이터 모델을 참고해 실제 거래 시나리오 10개 정도를 정의합니다. 부분 환불, 행사 취소, 지급 후 환불은 필수입니다.



2단계 — MySQL 기반 정산 모듈 구현

SettlementAgreement, Allocation, LedgerAccount, JournalEntry, SettlementBatch, Payout 등으로 모델링합니다. 모든 분개는 DB 트랜잭션으로 기록하고 거래 이벤트는 Outbox + SQS로 연결합니다.



3단계 — Blnk PoC

동일한 가상 주문·환불 데이터를 기존 MySQL 원장과 Blnk에 각각 적용해 잔액 일치, 멱등성, 조회 기능, 운영 복잡도를 비교합니다.



4단계 — 실정산 및 대사

실제 PG 정산 내역을 가져와 내부 원장과 비교한 후, 차이가 없는 정산 배치만 승인하고 지급 요청하도록 구성합니다.



참고로 Formance 최신 메인 브랜치의 v3는 기존 PostgreSQL 기반 v2와 달리 Raft 및 Pebble 스토리지 구조로 발전하고 있으므로, PoC할 때 버전을 명확히 구분해야 합니다. 

GitHub+1

또 하나 중요한 것은 국내 자금 보관 및 지급 구조의 법적 요건입니다. 2026년 12월 17일 시행 예정인 전자금융거래법 개정에는 PG 정산자금 보호와 전자지급결제대행 범위 변경이 포함됩니다. 톡켓이 직접 정산자금을 보유하는지, PG가 파트너에게 직접 지급하는지에 따라 검토해야 할 요건이 다르므로, 실제 송금 구조를 확정하기 전에 법률·PG 계약 검토가 필요합니다.

현재 톡켓에 적합한 접근은 다음과 같습니다.

정산 규칙과 계약 모델은 직접 구현하고, 복식부기 원장은 Blnk를 기준으로 설계하되 MySQL 자체 구현과 비교하는 방식입니다. 정산 기능 자체는 기존 모듈러 모놀리스 안에 두는 편이 초기 유지보수에 유리합니다.

특히 장기적으로 톡켓이 여러 사업자의 수익을 동시에 분배하는 플랫폼이 된다면, 단순한 partner_id + settlement_amount 구조가 아니라 거래당 여러 수취인과 지급 의무를 기록할 수 있는 범용 모델이 핵심 자산이 될 것입니다.
