# talket product variations

본 프로젝트를 시작하기 전에, 상품 생성·판매·수정·환불과 정산을 어떻게 나눌지 확인하는 프로토타입이다.

범위는 상품과 돈의 움직임이다. 유저, 로그인, 판매자 계정, PG 연동, 실제 송금은 만들지 않는다. 구매 주체는 이름 없는 주문으로 둔다.

## 계획

이 레포를 [commerce-study 분석](../commerce-study/분석/README.md)으로 읽고, 그 결론으로 남은 원형을 구현한다. 학습 노트는 옆 디렉터리 `commerce-study/분석`에 있다. 도메인 비교는 그 README, 한 주문에 여러 상품군을 넣는 뼈대는 [한-커머스로-모으기](../commerce-study/분석/한-커머스로-모으기.md), 기업 모델은 [추가 학습](../commerce-study/분석/추가-학습.md)과 각 프로젝트 폴더다.

아래 상품 원형·라이프사이클·환불·잠금 순서는 이 문서와 코드에 같이 있다. 점유는 전략 키로 갈리고, 주문·결제·원장은 그 바깥에 있다.

### 지금 코드가 어디에 있는지

한 커머스 v1의 겹은 테이블로 나뉘어 있다. 구매 화면의 회차·슬롯·구간·배송은 아직 픽스처이고, 서버 명령은 그 점유를 받는다.

| 겹 | 상태 |
|---|---|
| 카탈로그 | `products`, 옵션 축·값, `sellables`. 축이 재고를 나누면 판매 단위가 늘고, 직접입력은 `input_fields`로 줄 또는 수량 1개 아이템의 답에 복사된다 |
| 제안 | `offers`. 채널, 통화, 가격 키, 판매 기간. 단가는 판매 단위 행에 없다 |
| 가용성 | `availability_inventories`와 `availability_bindings`. 수량·슬롯·좌석·구간 저장도 `availability_`로 시작한다. 판매 단위와 재고는 다대다. 키는 `quantity.v1`, `seat.v1`, `interval.v1`. 슬롯과 배송은 `quantity.v1` |
| 홀드와 확정 | `holds`. 홀드가 점유를 잡고, 확정이 캡처와 판매 원장을 쓴다 |
| 주문 | 헤더와 여러 줄. 줄에 단가, 전략 키, 이번 결제액을 복사한다 |
| 돈 | `payments`는 캡처·환불. `ledger_entries`는 판매·수수료·환불·줄별 지급 예정. 지급 예정에는 수신자 칸이 있다 |
| 이행 | 줄의 `fulfilled`. 배송 재고 테이블은 없다. 출고 후 환불은 수량을 되돌리지 않는다 |

### 원형마다 열어 볼 노트

분석은 원형마다 같은 질문을 한다. 파는 단위는 무엇인가, 옵션이 새 판매 단위를 만드는가, 재고는 언제 점유되는가, 주문 줄에 무엇을 복사하는가, 환불 때 재고와 돈이 어떻게 갈라지는가.

| 이 레포 | 학습에서 여는 곳 | 분석에서 확정할 것 |
|---|---|---|
| 수량형 | Medusa·Saleor·Spree의 수량 카운터, Shopify `available`/`committed`, Magento 예약 로그 | 판매 순간 `on_hand`를 줄이는 지금 방식을 유지할지, 홀드와 출고를 나눌지. 공통 증감 함수는 두지 않는다는 이 문서의 결정을 유지한다 |
| 회차+좌석 | alf.io `SELECT … FOR UPDATE SKIP LOCKED`, 좌석 1행 | 회차 안의 좌석 행을 점유 테이블로 둔다. 좌석 번호는 옵션 축이 아니다 |
| 시간 슬롯 | Easy!Appointments의 슬롯 정원. 그 코드에는 `(제공자, 시작)` 유니크와 트랜잭션이 없다 | 슬롯 정원은 수량형과 같은 조건부 감소로 두고, 동시 삽입을 검사 후 쓰기로 끝내지 않는다 |
| 구간 점유 | QloApps의 객실×날짜, LibreBooking의 시간 겹침. 둘 다 DB 락이 약하다 | MySQL에 구간 배타 제약이 없다. 자원 행 잠금과 점유 키 중 하나를 이 슬라이스에서 고른다. 날짜·시간은 옵션이 아니다 |
| 배송 | 재고는 수량형. 출고 전/후는 Shopify `cancel` / `return`, Spree 출고 movement | 재고 테이블을 새로 만들지 않는다. 출고 상태는 주문 줄에 두고, 출고 전 환불만 수량을 되돌린다 |
| 한 주문의 여러 줄 | commercetools는 재고 모드를 라인마다 덮어쓴다. pretix는 이질적 라인이 한 주문에 있다 | 사용방식은 상품당 하나다. 티켓과 굿즈는 주문 줄 둘이다. 환불·정산은 줄 단위로 하고 원장은 하나로 합한다 |
| 가격 | Stripe는 금액을 고치지 않고 Price를 닫는다. 주문 줄 스냅샷은 Saleor·Medusa | 주말·성수기 가격은 옵션도 사용방식도 아니다. 팔린 단가는 주문 줄 복사본만 환불에 쓴다 |
| 돈 | 원장 append-only는 Magento 예약 로그, Stripe 환불, Odoo 이동과 같은 방향 | 잔액 컬럼을 만들지 않는다. 정정은 새 줄이다. 환불 재시도는 `ledger_entries.idempotency_key`로 한 결과만 낸다 |

Akeneo의 family / family variant는 옵션 축을 붙일 때 연다. 축이 판매 단위를 가르면 `sellables`가 늘고, 각인 문구처럼 재고가 안 갈라지면 주문 줄의 부가 정보로 남긴다. Odoo `stock.move`는 창고가 둘 이상일 때 연다. 이 프로토타입의 배송은 장소 이동이 아니다.

가져오지 않을 구현은 학습 노트에 이미 적혀 있다. Easy!Appointments와 LibreBooking의 검사 후 삽입, QloApps가 호텔 재고 대신 둔 더미 수량, 결제와 재고와 메일을 한 함수에서 끝내는 주문 확정, 상품마다 이벤트 id를 강제하는 모델.

### 순서

1. 수량형 판매는 홀드와 확정으로 나뉜다. `on_hand` 조건부 감소는 `quantity.v1` 안에만 있다. 완료.
2. 회차+좌석은 빈 좌석 행을 `held`로 바꾼다. 슬롯은 수량 재고의 대상이다. 구간은 자원 행을 잠그고 겹침을 본다. 배송은 수량 재고에 출고 상태만 줄에 둔다. 완료.
3. 사용 전 환불, 일부 환불, 사용 후 수수료, 구간 단축, 출고 후 배송, 한 주문에서 일부 줄만 환불한 정산은 `apps/api/test`에 있다. 자격, 응모, 외부 홀드, 수신자별 정산 분할은 없다.

정책 함수와 적용 트랜잭션은 이 문서의 [재고·환불 변경 전략](#재고환불-변경-전략)을 그대로 쓴다. 분석이 규칙을 바꾸면 정책만 고치고, 잠금 순서 `주문 → 점유 자원 → 원장 추가`는 적용 층에 둔다.

## 상품 원형

업종별 화면을 모듈로 만들지 않는다. 아래 다섯 원형이 티켓, 지정좌석, 쿠폰, 굿즈, 배송, 공간예약, 여행, 그리고 [스마트플레이스 예약상품 템플릿](https://help.naver.com/service/30026/category/5908?lang=ko)(일반형, 숙박형, 병의원형, 뷰티형, 회차형, 날짜선택형, 시작–종료시간형)을 덮는다. 갈라지는 지점은 재고를 점유하는 방식이다.

| 원형 | 점유 단위 | 포함되는 상품 |
|---|---|---|
| 수량형 | 개수 | 굿즈, 쿠폰, 비지정 티켓 |
| 회차+좌석 | 회차 안의 좌석 | 지정좌석 공연 |
| 시간 슬롯 | 슬롯당 정원 | 식당(일반형), 뷰티, 병원 |
| 구간 점유 | 시작–종료가 겹치면 불가 | 숙박, 공간대여, 여행 일정 |
| 배송 | 수량 + 출고 상태 | 배송 상품 |

쿠폰은 별도 원형이 아니다. 수량형에 소진(사용) 상태만 붙인다.

## 상품 목록

목록은 `products` 한 테이블이다. 업종마다 테이블을 나누지 않는다. 한 상품은 상품, 옵션, 사용방식이다.

- 상품: 이름, 판매 상태, 기본 가격, 사용방식 하나.
- 옵션: 고르는 축. 색, 사이즈, 좌석 등급, 인원, 객실 타입.
- 판매 단위: 옵션을 고른 결과로 주문에 오르는 한 줄. 축이 없으면 상품이 곧 판매 단위다.
- 사용방식: 위 다섯 원형 중 하나. 재고를 점유하는 방법이고, 환불 때 무엇을 되돌리는지도 여기서 갈린다.

사용방식은 상품당 하나다. 옵션은 사용방식을 바꾸지 않는다. 티켓과 굿즈를 함께 팔면 주문 줄이 두 개다.

점유 행은 사용방식별 테이블에 둔다. 수량, 회차와 좌석, 시간 슬롯, 구간. 좌석 번호, 예약 슬롯, 숙박 날짜는 옵션이 아니다. 배송의 재고는 수량이고, 출고 상태는 주문 줄에 붙는다. 주말·성수기 가격은 옵션도 사용방식도 아니며, 가격 규칙으로 따로 둔다.

## 공통 라이프사이클

모든 원형이 같은 흐름을 탄다.

`작성 → 판매중 → 점유(홀드) → 판매됨 → 사용/출고 → 변경 또는 환불 → 정산`

돈과 재고가 움직이는 지점은 이벤트다.

| 이벤트 | 재고 | 돈 |
|---|---|---|
| 판매 등록 | 판매 가능 수량을 연다 | 없음 |
| 점유 | 결제 전까지 잠시 빼 둔다 | 없음 |
| 점유 해제 | 되돌린다 | 없음 |
| 판매 | 점유를 확정한다 | 판매 금액 기록 |
| 사용/출고 | 소진. 좌석·슬롯·구간은 반환하지 않는다 | 없음 |
| 변경 | 점유 대상을 바꾼다 | 차액이 있으면 기록 |
| 환불 | 아직 사용·출고 전이면 재고를 되돌린다 | 환불 금액과 수수료 기록 |
| 정산 | 없음 | 판매, 수수료, 환불을 합쳐 지급 예정 금액을 낸다 |

정산은 상품 기능이 아니다. 위 이벤트를 줄로 쌓은 원장의 합이다. 줄의 종류는 판매, 수수료, 환불, 지급 예정이다.

## 환불 규칙

환불 가능 여부는 상품 종류가 아니라 다음 세 가지로 갈린다.

- 이미 사용했거나 출고했는가
- 전체 취소인가, 일부 취소인가
- 수수료를 빼는가

원형별 차이:

- 수량형, 회차+좌석, 시간 슬롯, 구간 점유: 사용 전 환불은 점유를 반환한다. 사용 후 환불은 돈만 다루고 재고는 되돌리지 않는다.
- 배송: 출고 전에는 수량 환불이다. 출고 후에는 이행 상태가 환불 가능 여부를 가른다.
- 구간 점유: 숙박·공간·여행은 구간 일부만 취소할 수 있다.
- 한 주문에 원형이 섞여 있으면(티켓 + 굿즈) 환불은 줄 단위로 하고, 정산은 남은 금액을 다시 합한다.

## 로컬 DB와 레이스 테스트

데이터베이스는 로컬 MySQL이다. 접속 정보는 `.env`에만 둔다. 이 파일은 커밋하지 않는다.

| 변수 | 값 |
|---|---|
| `DATABASE_HOST` | `localhost` |
| `DATABASE_PORT` | `3306` |
| `DATABASE_NAME` | `product-test` |
| `DATABASE_DIALECT` | `mysql` |

수수료, 원장 합계, 상태 전이는 `packages/domain` 단위 테스트로 검증한다. 동시에 같은 재고를 잡는 일은 MySQL 트랜잭션 테스트로 검증한다. 테스트는 HTTP보다 저장소에 커넥션을 여러 개 붙여 돌리고, 풀 크기(`DATABASE_POOL_MAX` 10) 안에서 8~10 동시면 충분하다.

각 원형이 추가될 때 같이 넣는 레이스 케이스:

- 수량형: 재고 1개에 구매 N건. 성공은 1건.
- 회차+좌석: 같은 회차의 같은 좌석 동시 점유. 확정은 1건.
- 구간 점유: 겹치는 예약 동시 삽입. MySQL에는 구간 배타 제약이 없으므로, 자원 행 잠금 또는 점유 키 중 무엇을 쓸지는 이 슬라이스에서 결정한다.
- 환불: 같은 주문 동시 환불. 원장은 한 번만 감소.
- 판매와 환불이 같은 재고를 동시에 건드리는 경우.

## 재고·환불 변경 전략

재고와 환불은 고칠 때마다 판매, 점유, 정산, 다른 원형까지 같이 깨진다. 안정은 테스트를 더 넣는 것보다, 한 번의 수정이 닿는 층을 하나로 줄이는 데 있다.

코드는 두 층이다.

- 정책: 순수 함수. 이 스냅샷에서 환불이 되는가, 수수료는 얼마인가, 원장 줄은 무엇인가, 재고를 되돌리는가. Nest와 DB를 모른다.
- 적용: 한 트랜잭션. 잠그고, 다시 읽고, 정책 결과를 조건이 맞는 행에만 쓴다. 잠금 순서와 조건부 쓰기 외에는 규칙을 갖지 않는다.

대부분의 수정은 정책에서 끝난다. 적용 층은 좌석을 어떻게 잠글지, 환불을 어떻게 한 번만 쓸지만 담당하고 거의 바꾸지 않는다.

쓰는 경로는 명령마다 하나다. `점유`, `판매 확정`, `변경`, `환불`. 공통 `재고 증감` 함수는 두지 않는다. 판매와 환불이 같은 헬퍼를 쓰면 한 조건 변경이 반대 경로로 샌다.

잠금 순서는 `주문 → 점유 자원 → 원장 추가`로 고정한다. 쓰기는 조건이 맞을 때만 성공한다. 재고가 요청 수량 이상일 것, 주문 상태가 판매됨일 것, 환불 누적과 요청의 합이 결제액을 넘지 않을 것. 성공한 행이 1이 아니면 그 명령은 거절이다.

원장은 추가만 한다. 잔액 컬럼을 고치지 않고, 이미 쓴 줄을 수정하지 않는다. 정정은 새 줄이다. 그래서 예전에 통과한 시나리오의 합은 새 규칙이 추가된 뒤에도 유지된다.

점유 전략(수량, 좌석, 슬롯, 구간, 배송)은 돈 계산을 호출하지 않는다. 환불 정책은 좌석 배치를 모른다. 정책이 `이 점유를 반환하라` 또는 `돈만 다뤄라`를 반환하면 적용 층이 실행한다.

재고·환불을 바꾸는 작업 순서:

1. 어떤 불변식이 바뀌는지 문장으로 적는다. 재고는 음수가 되지 않는다, 환불은 한 번만 원장에 남는다, 사용한 재고는 돌아오지 않는다, 원장 합이 잔액이다.
2. 그 문장을 깨는 시나리오 또는 레이스 테스트를 먼저 추가한다.
3. 정책과 적용을 같은 작업에서 같이 고치지 않는다.
4. 점유 전략만 바뀌면 해당 원형 레이스를 돌린다. 공유 불변식이 바뀌면 들어와 있는 원형의 레이스를 모두 돌린다.

동시성으로 진 명령과 규칙상 거절된 명령은 구분한다. 환불 재시도는 같은 키로 같은 결과를 돌려 원장이 두 번 깎이지 않게 한다.

## 레포 구조

pnpm 워크스페이스와 Turborepo다. 화면 라이브러리, 인증, 공통 UI 패키지는 두지 않는다.

```
apps/api              NestJS. 포트 3001. 헬스 체크와 수량형 명령
apps/web              Next.js. 포트 3000. 운영 콘솔
packages/domain       정책 층. 어휘, 수량 환불, 원장 합계
packages/contracts    API와 웹이 공유하는 타입
```

데이터베이스는 `mysql2` 풀이다. ORM은 두지 않는다. 이후 적용 층이 `WHERE` 조건과 반영된 행 수를 코드에서 그대로 보게 하기 위해서다. `.env`의 `localhost`는 소켓 대신 TCP `127.0.0.1`로 붙는다. 환경 변수는 저장소 루트의 `.env`만 읽는다.

`packages/domain`과 `packages/contracts`는 배포하지 않는다. 패키지 진입점은 `src/index.ts`이고, `dist`로 컴파일하지 않는다. API와 웹이 그 소스를 직접 읽는다. API 프로세스도 `dist` 대신 `src/main.ts`를 실행한다. `packages/domain`은 Nest와 `mysql2`에 의존하지 않으며, 테스트가 그 의존성이 들어오는 즉시 실패한다.

주문 줄은 판매 당시 이름, 단가, 전략 키, 이번 결제액을 복사한다. 상품 가격을 나중에 바꿔도 환불은 복사된 단가를 쓴다. 사용 전 환불은 재고를 되돌리고, 사용 후 수수료는 줄에 복사된 `fee_bps`를 쓴다. 기본 수수료는 0이다. 재고를 줄이는 홀드, 재고를 되돌리는 환불, 운영자의 재고 조정, 판매 단위를 바꾸는 변경은 각각 다른 `UPDATE`다. 성인·아동처럼 가격만 다른 경우는 가격 행 둘이고 재고 행은 하나다. 그 둘을 한 주문에 담으면 줄이 둘이다.

`pnpm test`는 각 테스트 시작 시 `product-test`의 상품, 주문, 원장 테이블을 비운다.

```
pnpm install
pnpm dev
```

콘솔은 http://localhost:3000 , API는 http://127.0.0.1:3001/health 이다. `pnpm test`는 도메인 어휘 테스트를 돌린다.

## 작업 순서

1. 상품 원형, 상태, 이벤트, 환불·정산 기준을 이 문서에 고정한다. 완료.
2. Turborepo를 얇게 만든다. `apps/api`, `apps/web`, `packages/domain`, `packages/contracts`. 로컬 MySQL 연결을 포함한다. 완료.
3. 수량형 하나로 생성 → 판매 → 수정 → 전액/부분 환불 → 정산 원장까지 관통한다. 끝에 초과 판매 레이스 테스트를 붙인다. 완료.
4. 점유를 포트로 둔다. 홀드와 확정, 여러 줄, 판매 단위와 재고의 다대다, 옵션으로 갈라지는 판매 단위, 직접입력, 가격 행, 회차+좌석, 슬롯, 구간, 배송 출고. 완료.
5. 유형을 가로지르는 환불·정산 시나리오. 사용 전 환불, 일부 환불, 사용 후 수수료, 구간 단축, 출고 후 배송, 한 주문 안에서 일부 줄만 환불한 정산. 완료. 수신자별 몫·발생·지급은 지급 예정 칸만 열어 두었다.

이 프로토타입의 결론으로 가져갈 결정은 하나다. 상품은 원형별 점유 전략으로 넣고, 환불과 정산은 하나의 원장으로 둔다.
